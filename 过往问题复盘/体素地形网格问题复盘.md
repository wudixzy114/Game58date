# 体素地形网格问题复盘

## 1. 现象

本次程序化体素地形开发中，先后出现了以下渲染异常：

1. 地形像一座又高又窄的摩天大楼。
2. 地形出现明显的“瑞士奶酪”式破碎空洞。
3. 只有某一个面是正常可见的，其他面发黑或像透明。
4. 顶面发黑，底面反而发亮。
5. 与其他方块接壤的内部面表现得像外表面一样被照亮。

这些现象看起来像多个问题，但最终发现它们并不是互相独立的。

## 2. 根本原因

### 2.1 第一层根因：区块空间摆放错误

最早的“摩天大楼”问题并不是地形高度本身异常，而是多个区块都生成在世界原点附近，视觉上叠在一起。

根因：

- 区块数据按 `chunkX/chunkZ` 正常生成了。
- 但是渲染实体在集成到场景时，没有乘上 `chunkSize * voxelScale` 放到对应世界位置。

结论：

- 这是一个**世界空间装配错误**，不是噪声生成错误。

### 2.2 第二层根因：地形生成逻辑过于“列填充”

最早版本的地形生成虽然已经是体素，但本质上仍然偏向“高度图 + 列填满”的思路，缺少稳定的 3D 密度场约束。

根因：

- 表层附近也允许洞穴 carve。
- overhang/cliff 贡献过大。
- 列填充主导，3D 结构不足。

结论：

- 这会把地形打碎成大量悬空和破洞块，形成“瑞士奶酪”观感。

### 2.3 第三层根因：贪心网格的面坐标框架不一致

这是最关键、也最隐蔽的问题。

在体素网格器中，最初尝试用一套“通用公式”同时覆盖 `+X/-X/+Y/-Y/+Z/-Z` 六个方向的面。这在概念上看似简洁，实际上非常容易出错。

具体错误有三类：

1. `Build()` 阶段用于确定 `du/dv` 尺寸的轴映射，和 `BuildMask()` 实际用的轴映射不一致。
2. `BuildMask()` 中正反面方向标记最初写反了。
3. `AddQuad()` 中六个方向的局部平面展开方式并不等价，不能靠一个简单公式可靠覆盖。

结论：

- 这类错误会直接导致某些面缺失、某些面法线反向、某些面明暗完全错误。

### 2.4 第四层根因：三角绕序和引擎 front-face 约定不匹配

最终导致“顶部黑、底部白、内部面像外部面一样亮”的真正核心，是**三角绕序错了**。

注意，这个问题不是单纯“右手系还是左手系”。

更准确地说：

- 我们的 CPU 网格数据生成出来后，
- 其三角顶点顺序与 Stride 当前对 front-face 的判定约定不一致，
- 引擎就把本该是外表面的三角当成 backface。

在这种情况下，即使关闭背面剔除：

- 面仍然会被绘制出来；
- 但 shader / lighting 可能把它们按背面处理；
- 于是就出现“顶面发黑、内部面发亮、上下受光颠倒”的现象。

结论：

- 真正的源头错误在 **CPU 侧 mesh data 的绕序定义**，而不是灯光本身。

### 2.5 第五层根因：第一次修复方向选错了层级

早期为了解决可见性问题，先后尝试了：

1. 改材质剔除模式。
2. 增加 emissive。
3. 调整方向光角度。
4. 调用 `ReverseWindingOrder()`。

其中前三个只能缓解现象，不能修复根因。

第四个思路方向对了一半，但实现层级仍然不对：

- `ReverseWindingOrder()` 作用于已经上传到 GPU 的 `MeshDraw`。
- 当前索引缓冲是运行时创建的 immutable GPU buffer。
- Stride 试图从 GPU buffer 反读 CPU 数据时，找不到 underlying CPU buffer，于是直接抛异常。

结论：

- **绕序问题必须在 CPU 生成 mesh data 时解决，而不是在 GPU 资源创建后再补救。**

## 3. 为什么第一次没有写对

原因不是某一行粗心，而是下面几个工程性误判叠加：

### 3.1 误把“通用抽象”当成“正确抽象”

最开始试图用一套统一的 `axis/u/v/normalSign` 逻辑覆盖所有方向，这种抽象虽然短，但并不稳。

对体素网格来说：

- 六个方向并不只是换个法线那么简单；
- 顶点顺序、局部平面坐标、绕序都需要严格逐面定义。

也就是说，最初的抽象“太聪明”，但不够可靠。

### 3.2 过早在渲染层补救，而不是回到数据源头

当出现黑面、透明面时，第一反应是：

- 是不是剔除有问题？
- 是不是光照方向有问题？
- 是不是材质太暗？

这些都值得查，但它们都在 mesh data 之后。

如果 mesh data 的面朝向本身错了：

- 后面所有层都只是在“带病运行”。

### 3.3 缺少“可验证的几何约定”

最开始没有把下面这件事显式固定下来：

- 对于 `+X/-X/+Y/-Y/+Z/-Z` 每一类面，
- 四个顶点的顺序是什么，
- 两个三角的绕序是什么，
- 该绕序在 Stride 中应该被视为 front-face 还是 backface。

没有这个明确约定，后续任何“看起来合理”的写法都可能刚好反掉。

## 4. 最终有效的修复

最终真正解决问题的步骤是：

1. 修正区块实体的世界坐标放置。
2. 将地形从简单列填充升级为更稳定的 3D 密度场，并限制表层 carve。
3. 将六个方向的面坐标框架改为**显式定义**，不再依赖错误的通用轴映射。
4. 在 CPU 侧直接翻转 quad 的三角索引顺序：

```csharp
0, 2, 1
0, 3, 2
```

而不是：

```csharp
0, 1, 2
0, 2, 3
```

5. 保留 `CullMode.None` 作为临时保险，避免再次被背面剔除误导。
6. 显式修正运行时方向光方向，让其从上往下照射地形。

## 5. 更好的方法：如何从根本上避免再次发生

### 5.1 为六个面建立显式的几何表，而不是靠公式猜

推荐做法：

- 建一个 `VoxelFaceDefinition[6]`
- 每个面显式定义：
  - 法线
  - 顶点局部坐标
  - UV 顺序
  - 三角绕序

不要再依赖一套复杂的 `axis/u/v/normalSign` 公式去“推导”六个方向。

### 5.2 在 CPU 网格阶段写单元测试

至少测试下面几类内容：

1. `+Y` 面的法线是否朝上。
2. `-Y` 面的法线是否朝下。
3. 每个面的两个三角法线方向是否一致。
4. 生成后的顶面在没有剔除时，是否被视为 front-face。

最重要的是：

- 让“几何正确性”在单元测试中被验证，
- 而不是等运行后通过肉眼看黑白面发现问题。

### 5.3 增加调试渲染模式

推荐长期保留两个调试模式：

1. **Face orientation mode**
   - `+X/-X/+Y/-Y/+Z/-Z` 六个方向分别显示不同颜色。

2. **Normal visualization mode**
   - 将法线映射到颜色输出。

这样任何面朝向问题都会第一时间被看出来，而不是靠猜。

### 5.4 区分“数据层问题”和“渲染层问题”

以后遇到类似异常时，排查顺序应该固定为：

1. 区块世界坐标是否正确。
2. mesh 顶点和索引是否正确。
3. 法线方向是否正确。
4. front-face / backface 判定是否正确。
5. 材质和剔除是否加剧了问题。
6. 最后再看灯光。

不要反过来从灯光和材质开始猜。

### 5.5 不要在 GPU 资源创建后再修绕序

如果绕序错了：

- 必须在 CPU mesh data 阶段改。

不推荐在 `MeshDraw` 上传后再调用需要 CPU readable buffer 的修正 API，因为：

- 运行时生成的 immutable buffer 默认没有 CPU 副本；
- 这类 API 很容易在真实运行时直接崩溃。

## 6. 结论

这次问题的核心不是“Stride 很奇怪”，也不是“灯光太暗”。

真正的根因是：

- **体素网格器的几何约定没有被明确定义并验证。**

后续所有黑面、缺面、反向受光、内部面发亮，本质上都是这个问题的不同表现。

如果以后继续扩展：

- 贪心网格
- 水体网格
- 碰撞网格
- 植被面片
- LOD 网格

都必须先把“面定义、绕序、法线、坐标框架”做成可验证的底层契约，而不是继续依赖肉眼调试。
